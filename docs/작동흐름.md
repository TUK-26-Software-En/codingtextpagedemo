## 작동 흐름 명세서

본 문서는 코딩 테스트 플랫폼의 실행 방법과 핵심 요청 처리 흐름을 정리한 명세서이다. 흐름 기술은 현재 구현된 서비스/퍼사드 코드를 기준으로 한다. 다이어그램 표현은 [Sequence Diagram.md](Sequence%20Diagram.md)를 함께 참조한다.

## 1. 실행 방법

### 1.1 로컬 (H2, 기본 프로파일)

```bash
./gradlew bootRun
```

- 기본 활성 프로파일 `local` → H2 인메모리 DB
- Swagger UI : `http://localhost:8080/swagger-ui.html`
- H2 콘솔 : `http://localhost:8080/h2-console` (JDBC URL `jdbc:h2:mem:codingtest`)

### 1.2 컨테이너 (PostgreSQL, docker 프로파일)

```bash
docker compose up --build
```

- `db`(PostgreSQL) healthcheck 통과 후 `app` 기동
- 활성 프로파일 `docker` → PostgreSQL, `ddl-auto=update`
- 데이터는 volume `pgdata`에 영속(`docker compose down` 후 재기동에도 유지, `-v` 시 삭제)

### 1.3 프런트엔드 (Phase 5)

브라우저로 `http://localhost:8080/` 접속 → 정적 FE(대시보드). Spring이 `resources/static`을 동일출처로 서빙하므로 FE가 `/api/**`를 그대로 호출한다. 헤더에서 개발용 로그인(USER, id) 후 문제 상세에서 코드 제출 → 실채점 결과(AC/점수) 확인.

## 2. 공통 요청 처리 라이프사이클

```
HTTP 요청 → JwtAuthenticationFilter → Controller → (Facade) → Service → Repository → DB
                                                          ↘ JudgeService (제출 시)
응답 ← ApiResponse<T> ← Controller
예외 ← GlobalExceptionHandler ← BusinessException(ErrorCode)
미인증 ← RestAuthenticationEntryPoint(401) / RestAccessDeniedHandler(403)
```

모든 정상 응답은 `ApiResponse<T>`로 래핑되고, 비즈니스 예외는 `GlobalExceptionHandler`가 표준 형식으로 변환한다.

### 2.1 인증/인가 (Phase 3)

JWT 기반 stateless. 읽기(GET)는 공개, 변경계(POST/PUT/DELETE)는 인증 필요(로그인·회원가입 제외).

1. `POST /api/auth/login {role, id}` → 역할별 존재 검증 후 `JwtProvider`가 HS256 토큰 발급
2. 이후 요청은 `Authorization: Bearer <token>` 헤더 → `JwtAuthenticationFilter`가 검증·인증 컨텍스트 설정
3. 토큰 없음/위조/만료로 보호 자원 접근 시 → `RestAuthenticationEntryPoint`가 401(`ApiResponse`) 반환

> 공개: 모든 GET, `/api/auth/login`, 회원가입(provider/user/supervisor), h2-console, swagger.

## 3. 핵심 흐름 — 문제 제출 및 채점

엔드포인트: `POST /api/submissions` (`SubmissionService.create`)

1. `userId`로 `User`, `problemId`로 `Problem` 조회 (없으면 예외)
2. `JudgeService.judge(problemId, language, sourceCode)` 호출 → `JudgeResult(status, score)`
   - 채점기는 `judge.mode` 설정으로 택일: `fake`(local/test, 항상 `AC`/100) 또는 `code`(docker, 실제 실행).
   - `code` = `CodeJudgeService`: 문제의 `Testcase`를 불러와 언어별 `LanguageRunner`(Python/Java)로 제출 코드를 실행하고 출력 비교. 전부 통과 시 `AC`/100, 첫 실패 시 `WA`/`TLE`/`RE`/`CE` 중 하나/0.
3. `Submission` 생성 — 제출 코드·언어·채점 상태·점수·제출 시각 저장
4. `updateUserProblem` — 해당 (user, problem)의 `UserProblem`이 있으면 상태 갱신, 없으면 신규 생성
5. `SubmissionResponse` 반환

> 채점·기록 저장·풀이 상태 갱신은 하나의 `@Transactional` 안에서 처리된다.

## 4. 핵심 흐름 — 대회 참가

엔드포인트: `POST /api/contests/{id}/join` (`ContestFacade.joinContest`)

1. `contestId`로 `Contest`, `userId`로 `User` 조회
2. `userContestRepository.existsByContestAndUser` 로 중복 참가 검사 → 중복 시 `DUPLICATE_PARTICIPATION` 예외
3. `UserContest` 생성(참가 시각 기록) 후 저장
4. `UserContestResponse` 반환

참가자 목록 조회: `GET /api/contests/{id}/participants` (`getParticipants`).

## 5. 핵심 흐름 — 시험 응시

엔드포인트: `POST /api/exams/{id}/take` (`ExamFacade.takeExam`)

- 대회 참가와 동일한 구조: 조회 → 중복 응시 검사 → `UserExam` 생성 → 응답
- 결과 목록 조회: `GET /api/exams/{id}/results` (`getResults`)

## 6. 운영(개설/배정) 흐름

- 문제 출제 후 카테고리 연결: `POST /api/problems` → `POST /api/problems/{id}/categories/{categoryId}`
- 대회 개설 → 문제 배정 → 감독자 배정: `POST /api/contests` → `/problems` → `/supervisors/{supervisorId}`
- 시험도 동일 패턴. 기관 소유 등록: `POST /api/organizations/{id}/{problems|contests|exams}/{targetId}`

전체 엔드포인트 목록은 [../IMPLEMENTATION_PROGRESS.md](../IMPLEMENTATION_PROGRESS.md) 및 Swagger UI에서 확인한다.

## 7. 배치 — 대회/시험 자동 마감·집계 (Phase 4)

종료 시각이 지난 대회/시험을 마감하고 결과를 집계한다. `@Scheduled` 주기 배치(`BatchScheduler`)와 수동 트리거(`POST /api/batch/aggregate`)가 동일 집계를 수행한다.

1. `findByEndTimeBeforeAndClosedFalse(now)` — 종료됐으나 미마감 대상 조회
2. 참가자별로 각 대회/시험 문제에 대해 기간 내 AC 제출 여부 확인 → solvedCount/totalScore 계산
3. 대회: 총점 내림차순 `rank` 부여 / 시험: 합격(≥만점60%)·등급(A/B/C/D/F) 산정
4. `close()`로 마감 표시 → 재실행 시 중복 집계 방지(멱등)

상세는 [Batch Diagram.md](Batch%20Diagram.md) 참조.

## 8. 향후 흐름(설계)

- 채점 격리 강화: 현재는 앱 컨테이너 내부 실행(격리 약함). 운영 수준은 제출별 컨테이너/별도 judge 서비스로 분리 예정
- 실시간 랭킹/부정행위 감지, 프런트엔드 연동(Phase 5)
